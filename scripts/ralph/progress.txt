**Learnings for future iterations:**
- MT103 field structure: tag (2 digits + optional letter), multiple options (A/B/C/D/F/K) for party identification fields
- Party identification fields follow pattern: A=BIC, B=Location, C=Party Identifier only, D=Name&Address, F=Structured
- Composite fields like 32A break down into subfields: date (YYMMDD) + currency (3!a) + amount (15d with comma decimal)
- SWIFT format notation: 4!a = exactly 4 alpha, 2!c = exactly 2 alphanumeric, 15d = up to 15 digits with decimal, 4*35x = up to 4 lines of 35 chars
- Field 50 (Ordering Customer) must have exactly one option present (A, F, or K)
- Field 59 (Beneficiary) must have exactly one option present (no suffix, A, or F)
- Optional account lines prefixed with / and max 34 characters appear before BIC or name/address
- CRLF (\\r\\n) used as line separator in multi-line fields within Block 4
- Charge bearer field 71A values: BEN (beneficiary pays all), OUR (ordering customer pays all), SHA (shared) - SEPA requires SHA
- Format patterns use character classes matching SWIFT character sets X (alphanumeric + basic punctuation), Y (uppercase + digits + special), Z (extended)
- Field ordering is critical: mandatory fields in sequence, optional fields have specific positioning rules relative to each other
- Common field tag patterns: 5x fields = parties, 3x fields = amounts/currencies, 7x fields = charges/info, 2x/1x = references/codes
- BIC format in fields: 4!a2!a2!c[3!c] = institution(4) + country(2) + location(2) + optional branch(3)
- The schema is reusable for MT202, MT940, MT942 specifications with same structure
